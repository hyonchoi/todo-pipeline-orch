# Executable Harness Fixture Contract

## Problem

The `happy-path` harness fixture describes TODO-1 as a “simple data
transformation module” but does not define its input, output, public interface,
behavior, implementation language, or acceptance criteria. Phase 2 correctly
rejects that TODO as ambiguous, so a live happy-path harness run blocks before
development.

## Design

Keep the pipeline prompts and Autoplan ambiguity gate unchanged. Expand only
the mock TODO generated by `hermes_pipeline.harness._get_todos_for_fixture()`.
The fixture will define a small Python transformation with:

- a named module and function;
- a concrete input and return type;
- deterministic normalization behavior;
- empty-input behavior;
- a requirement to avoid external dependencies; and
- executable acceptance criteria.

The contract remains intentionally small so external agents can plan,
implement, review, and test it without product decisions or user input.

## Data Flow

`create_mock_project()` writes the enriched TODO to `TODOS.md`. The normal
selection and phase-registration paths pass only the TODO identifier to phase
prompts. Autoplan reads the repository's `TODOS.md`, finds the complete
contract, and can create the plan and feature branch without clarification.

No fixture-specific requirements are duplicated in phase YAML or Python prompt
wrappers.

## Error Handling

Unknown fixture names continue to raise `ValueError`. The Autoplan instruction
to exit on genuinely ambiguous TODOs remains unchanged. This fix makes the
fixture valid rather than weakening that failure behavior.

## Verification

Add a regression test against the generated mock project's real `TODOS.md`.
The test will assert the named interface, deterministic behavior, edge case,
implementation constraint, and acceptance criteria are present. It must fail
against the current underspecified fixture and pass after the fixture is
enriched.

Run the focused harness tests, then the full locked test suite. Finally, inspect
the original blocked Kanban task and report that it belongs to the old retained
harness run; a fresh harness run is required to exercise the corrected fixture.

## Scope

In scope:

- `hermes_pipeline/harness.py`
- fixture regression coverage in `tests/test_harness.py`

Out of scope:

- changing Autoplan or its ambiguity policy;
- adding fixture content to phase prompts;
- changing Hermes dispatch or external-client selection; and
- mutating or resuming the already-blocked retained harness task.
