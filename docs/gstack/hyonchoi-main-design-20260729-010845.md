## Problem Statement

Bundled phase profiles tell workers to use skills "in Claude Code" and invoke
them with Claude's `/skill-name` syntax. The project supports installing skills
for both Claude and Codex, but selecting Codex does not change these phase
instructions. A Codex worker therefore receives misleading or unusable prompts.

TODO-41 adds a global client selection that renders correct client-specific
phase instructions. This setting affects prompt text only. Hermes remains the
execution path and continues to own scheduling, assignees, profiles, models, and
task dispatch.

## What Makes This Cool

One machine-level setting makes every bundled phase prompt speak the selected
client's native language without duplicating pipeline profiles:

- `claude` renders `Claude Code` and `/skill-name`.
- `codex` renders `Codex` and `$skill-name`.

The phase workflow remains identical. Only the instructions crossing the Hermes
worker boundary change.

## Constraints

- Preserve Hermes as the sole execution and scheduling path.
- Do not change Hermes models, profiles, assignees, task commands, or
  authentication.
- Preserve existing behavior when the setting is absent.
- Keep the global config a whole-file configuration selected through the
  existing discovery rules. Do not add an individual environment-variable
  override for this field.
- Keep one canonical set of bundled phase profiles.
- Support only the closed values `claude` and `codex`.
- Treat skill installation and discovery as a client-support prerequisite, not
  a responsibility of phase rendering.
- Update both production registration and the harness registration path.
- Do not mechanically replace `/` characters; file paths, URLs, and ordinary
  prose must remain unchanged.

## Premises

1. `agent_client` is a global `Config` field with allowed values `claude` and
   `codex`. Its default is `claude`, preserving existing configurations and
   direct callers.
2. The field controls prompt vocabulary only. It does not choose or launch an
   executable.
3. A shared phase profile is supported for a selected client only when every
   skill referenced by that profile can be installed and discovered by that
   client. Because Hermes workers may run outside the local `tpo` host,
   registration cannot prove remote availability. The implementation publishes
   an explicit prerequisite matrix and tests project-owned discovery contracts
   without installing skills during rendering.
4. Client vocabulary includes at least the product label and explicit skill
   invocation prefix. Claude Code uses `/`; Codex uses `$`.
5. Client selection is resolved once through the existing global config and
   passed explicitly through registration to rendering. Low-level render code
   does not reread global configuration.
6. Bundled templates must fail visibly when a required client placeholder is
   unresolved. Silently returning an unrendered template is not acceptable.

`Conditional` means TPO guarantees correct prompt rendering when prerequisites
are present; it does not guarantee that an independently distributed skill is
installed on a particular Hermes worker.

`Unverified` means the profile remains bundled but must not be advertised as
Claude- or Codex-compatible until the external plugin's exact provisioning
command, discovery mechanism, and invocation syntax are verified for that
client. That verification is a prerequisite for changing the matrix status; it
is not guessed by TODO-41.

Registration must not fail based on local skill discovery because the worker
environment may be remote or containerized. Documentation and `tpo doctor`
output, if doctor already has the selected worker environment in scope, may
warn that skill availability is a prerequisite. Adding remote skill inventory
or installation is separate work.

## Landscape Findings

Claude Code and Codex both use `SKILL.md` workflows and can activate skills
explicitly or by matching their descriptions. Their explicit invocation and
repository discovery conventions differ:

- Claude Code: `/skill-name`, with project skills under `.claude/skills/`.
- Codex: `$skill-name`, with repository skills under `.agents/skills/`.

The common skill standard supports a shared phase workflow. The differing
invocation vocabulary justifies render-time client fields rather than duplicate
profiles.

## Cross-Model Perspective

An independent Codex subagent and Claude CLI cold read agreed on the central
design: a typed global client value, fixed vocabulary, shared templates, and
explicit propagation into `_render_phase_prompt()`.

Both found a second runtime path that is easy to miss: the harness also
registers phase prompts and must receive the same `agent_client` value.

The Codex review identified the strongest premise challenge: syntactically
correct `$skill-name` prompts are still broken when the named skill is absent
from Codex's discovery roots. That finding revised Premise 3 and adds a
client-support prerequisite plus installation/discovery acceptance coverage.

The Claude review questioned whether prompt-only behavior could lie to an
underlying Claude-specific dispatcher. Repository tracing resolves that concern:
the rendered text becomes a Hermes kanban task body. The orchestrator does not
invoke a Claude or Codex skill dispatcher directly, so execution routing remains
out of scope.

Both reviews also warned against broad string replacement. Client-aware fields
must cover the product name and invocation prefix explicitly.

## Approaches Considered

### Approach A: Targeted Post-Render Substitutions

Render the current prompt, then replace known Claude-specific phrases and skill
references.

This is the smallest diff, but it creates an expanding hidden replacement list.
New prompts can silently reintroduce Claude wording, and broad replacements can
damage paths or unrelated slash characters. Rejected because correctness would
depend on remembering every phrase variant.

### Approach B: Typed Vocabulary Placeholders in Shared Profiles

Add a typed client setting and fixed vocabulary, place explicit client fields in
the shared YAML profiles, and pass the selected value through all registration
paths into strict rendering.

This makes client-specific text visible where prompts are authored, keeps one
profile source of truth, and enables complete rendered-profile tests. Selected.

### Approach C: Client Overlays

Keep canonical profiles client-neutral and merge separate Claude/Codex overlay
files at load time.

This supports large future differences, but adds overlay precedence, packaging,
validation, and missing-override behavior before there is evidence that two
vocabulary fields require a new merge system. Rejected as premature.

## Recommended Approach

Implement Approach B.

### Configuration contract

Define:

```python
AgentClient = Literal["claude", "codex"]
```

Add `agent_client: AgentClient = "claude"` to `Config` and
`agent_client: claude` to the generated global-config skeleton. The existing
dataclass-driven config key and `Literal` coercion paths power `tpo config
init`, `get`, and `set`. Existing tests already establish accepted and rejected
`Literal` values plus source-wrapped config errors. Add field-level tests for
YAML null, case mismatch, and CLI validation before relying on this behavior.

If those tests expose a gap, improve the single shared dataclass coercion layer
so every `Literal` field receives the same behavior. Do not create an
`agent_client`-specific parallel validator.

Invalid, null, or case-mismatched values fail with the config source and allowed
values. Do not add `TPO_AGENT_CLIENT` or `PIPELINE_AGENT_CLIENT`.

### Fixed client vocabulary

Keep labels in code, not user configuration:

| Client | Product label | Skill prefix |
|---|---|---|
| `claude` | `Claude Code` | `/` |
| `codex` | `Codex` | `$` |

The closed config type plus fixed mapping prevents arbitrary prompt text from
entering templates.

### Shared profile templates

Replace actual client-dependent text in both bundled phase profiles with named
fields:

```yaml
prompt: |
  Use the gstack {skill_prefix}autoplan skill in {agent_product}.
```

Apply the same treatment to secondary references such as `/review's`, `/ship`,
and namespaced `agent-skills:*` skills. Do not alter file paths, URLs, phase
names, tools, turns, or timeout values.

Do not duplicate whole prompt bodies by client.

Exact expected forms:

| Template intent | Claude output | Codex output |
|---|---|---|
| Ordinary skill | `Use the /autoplan skill in Claude Code.` | `Use the $autoplan skill in Codex.` |
| Possessive reference | `Follow /review's fix loop.` | `Follow $review's fix loop.` |
| Namespaced skill | `Use /agent-skills:ship in Claude Code.` | `Use $agent-skills:ship in Codex.` |

These examples establish the current grammar. If a future client needs more
than a prefix difference, add a new explicit vocabulary field or per-client
reference value. Do not make the renderer infer grammar with regexes.

### Runtime propagation

Use the existing production seam:

```text
cli._tick_project(config)
  -> register_todo_phases(..., agent_client=config.agent_client)
  -> _render_phase_prompt(..., agent_client=agent_client)
```

Propagate the same value through the harness path:

```text
run_harness(config)
  -> harness polling/registration
  -> register_todo_phases(..., agent_client=config.agent_client)
```

Keep `agent_client="claude"` defaults on lower-level rendering and registration
APIs where needed for compatibility with direct callers and existing tests.
Production callers must pass the resolved value explicitly.

### Rendering contract

Use strict named formatting for repository-owned phase templates.

Before formatting, parse the template fields and allow only:

- `todo_id`
- `tick_id`
- `project_slug`
- `agent_product`
- `skill_prefix`

Unknown fields, positional fields, malformed braces, or unresolved allowed
fields raise `PhasePromptRenderError`, a `ValueError` subclass. The error
message names the phase/template source when available and the offending field
or formatting problem. Registration aborts before emitting the affected Hermes
task.

Remove the current broad `KeyError`/`IndexError` fallback that returns the
template verbatim. `_render_phase_prompt()` is private and its documented
templates are repository-owned, so silently preserving malformed external
templates is not a supported compatibility contract.

The `agent_client="claude"` default remains for direct callers; formatting
tolerance does not. Tests must cover ordinary literal braces using escaped
`{{` and `}}`, all five allowed fields, unknown fields, positional fields,
malformed braces, and unresolved client fields.

The renderer must also:

- reject unknown `agent_client` values before selecting vocabulary;
- never perform broad slash or product-name replacement;
- preserve existing TODO/tick/project, Spec, and Reference rendering;
- preserve `$` as literal task-body text without sending it through a shell.

### Client-support prerequisite

Selecting a client does not install skills. Documentation must tell installed
users to provision every skill in the matrix for the chosen profile and client
before running the pipeline.

TODO-41 tests what this repository owns:

- every bundled prompt's skill references appear in the prerequisite matrix;
- each phase/client render snapshot uses the expected product and invocation
  grammar;
- project-owned skill installation tests continue to validate Claude and Codex
  discovery roots for skills this package actually distributes.

Live installation and invocation of gstack, superpowers, and agent-skills are
release-qualification checks for those external distributions, not hermetic
TODO-41 tests. If current evidence cannot establish an external skill on a
client, its matrix status remains `Unverified`; documentation must not call it
unconditionally supported.

## Open Questions

No product or rendering-contract decisions remain open.

The matrix records external distributions as conditional or unverified, as
shown per row, because worker availability cannot be proven locally. A future
worker-capability handshake could make that preflight enforceable, but it is
separate from TODO-41.

## Success Criteria

- With no `agent_client` key, effective configuration is `claude`.
- `tpo config init` emits `agent_client: claude`.
- `tpo config get agent_client` reports the effective value and source using
  existing CLI semantics.
- `tpo config set agent_client codex` persists and reloads `codex`.
- Invalid, null, and case-mismatched values fail with actionable errors.
- Every bundled phase in both profiles renders without unresolved client
  placeholders for both allowed clients.
- Claude rendering contains `Claude Code` and correct `/skill` references, with
  no Codex-only `$skill` references.
- Codex rendering contains `Codex` and correct `$skill` references, with no
  stale `Claude Code` wording or client-dependent `/skill` references.
- Ordinary, possessive, and namespaced references match the exact examples in
  this document.
- Unknown fields, positional fields, malformed braces, and unresolved client
  fields fail with `PhasePromptRenderError` before the affected task is
  registered.
- Existing TODO, tick, project, Spec, and Reference rendering remains correct.
- Production tick registration and harness registration both use the configured
  client.
- Default lower-level API behavior remains Claude-compatible for existing direct
  callers.
- Every bundled skill reference appears in the prerequisite matrix.
- Project-owned installer tests continue to prove both client discovery roots;
  external skill distributions remain explicit conditional prerequisites.
- README and CLI reference distinguish agent client, pipeline profile, Hermes
  assignee/profile, and model selection.
- Focused config/render/registration tests, the full non-eval test suite, Ruff,
  and `git diff --check` pass through RTK-prefixed commands.
