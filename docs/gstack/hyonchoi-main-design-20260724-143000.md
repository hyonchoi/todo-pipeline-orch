## Problem Statement

The project has two console-script entry points (`pipeline-watch` and `hermes-pipeline`) both pointing to the same `hermes_pipeline.cli:main`. Users install with `uv tool install` or `uv run` but get a long, unintuitive command name. Meanwhile, the `todos-manager` skill lives outside the package at `skills/todos-manager/` — breaking `uv tool install` distribution since users must manually clone that directory.

## What Makes This Cool

A single short command `tpo` — typed in 15ms, memorable, and the basis for a clean subcommand structure (`tpo init`, `tpo doctor`, `tpo skills install`). The `tpo skills install` subcommand self-boots the todos-manager into the user's `~/.claude/skills/` without leaving the terminal.

## Constraints

- Strict rename only for TODO-33 — no API surface changes, no new subcommands beyond `skills`
- TODO-34 must package non-Python files (SKILL.md + sections/) as package data via hatchling
- `uv tool install` distribution model must work end-to-end after the change
- The internal Python package name `hermes_pipeline` stays unchanged (only the console script changes)
- Python 3.12+, hatchling backend, uv-managed

## Premises

1. A short, memorable CLI name reduces friction — `tpo` > `pipeline-watch` > `hermes-pipeline`
2. Embedding the todos-manager skill as package data is the right solution for `uv tool install` compatibility
3. The rename is mechanical — all occurrences of `pipeline-watch` and `hermes-pipeline` in docs, tests, and source can be replaced with `tpo` in a single pass
4. Existing users with `pipeline-watch` or `hermes-pipeline` on their PATH get a deprecation shim (see TODO-33 update below), not an immediate break.

## Approaches Considered

### Approach A: Quick rename + separate TODO-34 branch
Do TODO-33 as a strict find-and-replace across all files, ship it, and tackle TODO-34 in a separate branch. Minimal risk, no architecture design needed for the skill embed.

**Trade-off:** Two PRs, two version bumps, two review cycles. The `tpo` subcommand architecture isn't planned, making TODO-34 harder to scope later.

### Approach B: TODO-34 only, leave TODO-33 for later
Build the `tpo skills install` subcommand first on a new console entry point, leave `pipeline-watch` intact. Add `tpo` alongside existing scripts, deprecate later.

**Trade-off:** Two console scripts coexisting is messy. Doesn't solve the core ergonomics problem (long command name).

### Approach C: Design full `tpo` CLI architecture, implement both together
Design the subcommand structure for `tpo` first (including where `skills` fits), then implement the rename AND the skill embed in one change.

**Trade-off:** More work in a single PR but both items share the same entry point. One bundled commit, one review.

## Recommended Approach

**Approach C** — design the full `tpo` CLI architecture and implement TODO-33 + TODO-34 together.

**Rationale:** Both changes touch `pyproject.toml` `[project.scripts]` and `cli.py`. Bundling avoids updating the entry point twice. The `skills` subcommand is small enough to fit in one PR — it follows the `_cmd_install_profile` pattern: parse args, locate packaged data, copy to target directory. No CLI architecture redesign is needed; the existing argparse subparser structure is sufficient.

### TODO-34: Embed todos-manager + `tpo skills install` subcommand

**Package structure:**
```
hermes_pipeline/
  data/
    __init__.py            # Single package anchor — makes data/ traversable
    skills/
      todos-manager/       # Data directory — hyphen name, no __init__.py needed
        SKILL.md
        sections/
          acceptance-scenarios.md
          auto-research.md
          convert-mode-b.md
          entry-boundary.md
          error-messages.md
          id-assignment.md
          list.md
          revise.md
          schema.md
```

**Why `data/` and not `skills/` at the package root:** The skill files are markdown data, not Python submodules. Placing them under `data/` avoids needing `__init__.py` in every subdirectory and preserves natural directory names (hyphens). One `__init__.py` at the data root is the only Python package requirement.

**Path resolution:** A shared `_resolve_bundled_dir(*parts)` helper (new — retrofits `bundled_profile_dir()` in `contract.py` to use it too) resolves `importlib.resources.files("hermes_pipeline.data").joinpath(*parts)`. Real fallback: if `Path(traversable)` raises (zip-wheel install, non-filesystem Traversable), extract to a `tempfile.mkdtemp()` directory instead of assuming filesystem installs unconditionally. This replaces the docstring-only caveat currently in `bundled_profile_dir()`.

**pyproject.toml package data:** Hatchling's `packages = ["hermes_pipeline"]` (already set in pyproject.toml) includes all files in the package directory tree by default, including non-Python files. No `force-include` block is needed.

**New CLI subcommand:** Add `skills` subparser to `build_parser()` in `cli.py` with a single `install` sub-subcommand:
```
tpo skills install [--target {codex|claude|all}] [--scope {user|project}] [--force]
```
- `--target`: `codex` → `.agents/skills`, `claude` → `.claude/skills` (default: `claude`), `all` → both
- `--scope`: `user` → `~/` prefix (default), `project` → repo-root prefix
- Target directory receives a `todos-manager/` subdirectory (e.g., `~/.claude/skills/todos-manager/`)
- `--force`: without it, existing files are still overwritten (reinstall is idempotent by default — no separate confirmation step); `--force` exists for scripting/non-interactive clarity but doesn't change copy behavior beyond skipping any future confirmation prompt
- `--target all` partial failure: attempt both writes independently (best-effort), report per-target success/failure, exit 1 if either failed

**`_cmd_skills_install` implementation:** Pattern from `_cmd_install_profile` (Problem/Cause/Fix structured errors for source-missing, permission-denied):
1. Resolve source via `_resolve_bundled_dir("skills", "todos-manager")`
2. Resolve target(s) from `--target`/`--scope` combination
3. `shutil.copytree(source, target, dirs_exist_ok=True)` per target — always overwrites, no separate confirmation
4. Print per-target success/failure; exit 1 if any target failed

**Bootstrap config bypass:** `main()` currently calls `Config.from_env()` unconditionally before dispatch. `skills install` (and other bootstrap-type subcommands) skip this — they don't need pipeline runtime config (state dir, lock dir, etc.) to copy files.

**v1 scope:** `--target all --scope user` covers both `~/.claude/skills` and `~/.agents/skills` in one command. `--scope project` is available for repo-local installs.

- `uv build` produces a wheel that includes `hermes_pipeline/data/skills/todos-manager/` as package data (verifiable via `unzip -l dist/*.whl | grep skills`)
- New tests for `tpo skills install`:
  (a) mocked copy verifies files written per target
  (b) reinstall overwrites existing files without error
  (c) target directory created if missing
  (d) package data discoverable via `importlib.resources`
  (e) `--target`/`--scope` argument parsing produces correct path combinations
  (f) `_resolve_bundled_dir()` fallback path (mocked non-filesystem Traversable)
  (g) permission-denied on target produces Problem/Cause/Fix error, exit 1
  (h) `--target all` partial failure reports per-target status, exit 1
  (i) deprecated `pipeline-watch`/`hermes-pipeline` shims print warning and still dispatch correctly

## Distribution Plan

`uv tool install` from PyPI or local path. The wheel must include the skill data files. Users install and run `tpo skills install` to bootstrap the todos-manager skill. No CI/CD change needed — existing GitHub Actions build and test workflow works with the new entry point.
