## Problem Statement

Two small-looking TODOs both protect the maintainer workflow from silent state drift.

`TODO-35` hardens `tpo skills install`: the current installer overwrites an existing
`todos-manager` destination by default via `shutil.copytree(..., dirs_exist_ok=True)`.
That makes repeated installs look harmless, but it can silently replace local edits or
fail late on structural conflicts. The desired behavior is fail-on-exists by default,
explicit `--reinstall` for replacement, and a symmetrical `tpo skills uninstall` command
with confirmation.

`TODO-38` moves TODO ID assignment from per-add archive scans and the gitignored
`.hermes/todo_id_counter` cache to a tracked `NEXT_TODO_ID: <n>` line in `TODOS.md`.
The current bundled skill still says next ID is `max(all IDs in TODOS.md +
TODOS-archive.md) + 1`, so this is a schema/workflow migration, not just an
implementation tweak.

## What Makes This Cool

The payoff is trust. Future agents can run `tpo skills install` without wondering
whether they overwrote a skill, and `todos-manager --add` can assign IDs from tracked
project state instead of rediscovering history every time. The maintainer experience
becomes explicit: destructive replacement has a named flag, and ID drift self-heals
through audit rather than becoming a hidden fork-local bug.

## Constraints

- Python 3.12+ project managed by `uv`.
- Current installer lives in `hermes_pipeline/cli.py` around the `skills` subparser
  and `_cmd_skills_install`.
- Existing installer tests live in `tests/test_skills_install.py`; one current test
  asserts overwrite-by-default and must flip.
- Bundled skill source lives in `hermes_pipeline/data/skills/todos-manager/`.
- The todos-manager deterministic test oracle lives under `tests/skill-test-environment/`.
- `Spec:` and `Reference:` fields remain `--revise`-only and must not be guessed.
- `.hermes/todo_id_counter` is explicitly out of scope for deletion in `TODO-38`.

## Premises

1. `TODO-35` should intentionally break double-run install scripts unless they pass
   `--reinstall`, because silent overwrite is the bug.
2. `TODO-38` changes the canonical TODOS schema and bundled skill docs, not only
   runtime code.
3. `.hermes/todo_id_counter` stays as compatibility/cache state for now, but
   `TODOS.md` becomes the source of truth for next ID.
4. Both TODOs need tests for failure paths, not just happy path installs/adds.

## Approaches Considered

### Approach A: Minimal Viable Patch

Add `--reinstall`, make existing destinations fail by default, add
`skills uninstall`, and update `id-assignment.md` plus schema text to mention
`NEXT_TODO_ID`. Tests cover parser flags, existing-destination failure,
reinstall replacement, uninstall confirmation, and basic next-ID migration.

Effort: S
Risk: Medium

Pros:
- Smallest diff and fastest path to implementation.
- Keeps `TODO-35` almost entirely inside `cli.py` and its existing tests.
- Handles the most visible `TODO-38` documentation drift.

Cons:
- Risks duplicating ID reconciliation behavior across docs and tests.
- Easy to update the preamble but miss the test oracle or audit report behavior.
- Makes later `.hermes/todo_id_counter` cleanup harder to reason about.

Reuses:
- Existing `skills` subparser pattern in `build_parser()`.
- Existing structured Problem/Cause/Fix installer errors.
- Existing todos-manager section layout.

### Approach B: Shared Reconciler Foundation

Implement a small TODO metadata/reconciliation helper used by the packaged skill
test oracle and any Python-side support, with `NEXT_TODO_ID` parsing, conflict
detection, audit repair, and archive fallback in one place. Keep `TODO-35`
scoped to `cli.py`, while `TODO-38` updates schema, id-assignment docs, tests,
fixtures, and audit behavior around the same helper contract.

Effort: M
Risk: Medium

Pros:
- Gives future agents one reliable contract for TODO ID state.
- Makes conflict-triggered self-healing testable instead of prose-only.
- Aligns schema text, id-assignment docs, audit behavior, and tests.

Cons:
- Slightly larger than the current `Effort S` label for `TODO-38`.
- Requires care to avoid turning the skill docs into a Python runtime dependency.
- Needs migration tests for preamble insertion and legacy projects.

Reuses:
- `tests/skill-test-environment/skill_logic.py` as the deterministic oracle surface.
- `sections/id-assignment.md`, `sections/schema.md`, and audit output conventions.
- Existing archive scan logic as the rare reconciliation fallback.

### Approach C: Split Ship Order

Ship `TODO-35` first as an isolated CLI behavior PR, then handle `TODO-38` as a
separate schema migration PR with focused review. The implementation does not mix
skill installation safety with tracked TODO metadata.

Effort: S + S/M
Risk: Low per PR, Medium total

Pros:
- Easier review and bisection.
- Reduces chance of blocking installer hardening on schema migration details.
- Lets `TODO-38` get a dedicated design/test pass.

Cons:
- Two branches, two review cycles, and two release decisions.
- Slower arrival at the actual tracked-counter fix.
- Leaves the known ID-assignment drift in place after the first PR.

Reuses:
- Existing TODO branch assignments: `feat/skills-install-reinstall` and
  `feature/todos-next-id-tracking`.

## Recommended Approach

Choose Approach B: Shared Reconciler Foundation.

`TODO-35` and `TODO-38` should not be tangled in one module, but `TODO-38` should
not be reduced to a text edit. The critical path is a single testable contract:

1. `TODOS.md` preamble contains `NEXT_TODO_ID: <n>`.
2. `--add` reads that value in O(1) on the common path.
3. Before writing `TODO-<n>`, the workflow verifies the ID is not already present
   in active TODOs.
4. On conflict, it runs the audit reconciliation scan across `TODOS.md` and
   `TODOS-archive.md`, corrects `NEXT_TODO_ID` in place, logs the correction,
   and continues without asking the user.
5. Standalone `--audit` performs the same reconciliation and reports what changed.
6. `.hermes/todo_id_counter` may still be updated as compatibility/cache state, but
   it no longer decides the next ID.

For `TODO-35`, keep the behavior direct:

1. `tpo skills install` fails if any destination already exists.
2. `tpo skills install --reinstall` removes the existing `todos-manager` destination
   and copies the bundled version.
3. `tpo skills uninstall` removes selected installed destinations after confirmation.
4. Non-interactive uninstall should have an explicit yes flag, preferably `-y/--yes`,
   matching the confirmation style already used by `hermes profile delete`.
5. `--target all` should report per-target outcomes and exit nonzero if any selected
   target fails.

## Open Questions

1. Should the installer replacement flag be named only `--reinstall`, or should
   `--force` be accepted as a deprecated alias for script familiarity? Default
   recommendation: only `--reinstall`, because the TODO explicitly names it and
   the operation is clearer than generic force.
2. Should `tpo skills uninstall` support `--scope project` from day one?
   Default recommendation: yes, because install already supports user/project scope.
3. Should `--audit` modify `TODOS.md` when only `NEXT_TODO_ID` is wrong?
   Default recommendation: yes, because `TODO-38` explicitly calls for audit
   reconciliation, and stale tracked metadata is a format error with a mechanical fix.

## Success Criteria

- `tpo skills install` succeeds when the destination is absent.
- `tpo skills install` fails with a structured Problem/Cause/Fix message when the
  selected destination already exists and `--reinstall` is not passed.
- `tpo skills install --reinstall` replaces the existing destination and succeeds.
- `tpo skills uninstall` refuses to delete without confirmation unless `--yes` is passed.
- `tpo skills uninstall --target all --scope user --yes` removes both supported user
  destinations and reports per-target results.
- New or converted `TODOS.md` files include `NEXT_TODO_ID: <n>` in the preamble.
- `todos-manager --add` uses `NEXT_TODO_ID` on the common path and increments it
  after a successful write.
- If `NEXT_TODO_ID` points at an existing TODO, add/audit reconciles by scanning
  `TODOS.md` plus `TODOS-archive.md` and writes the corrected next value.
- Legacy projects without `NEXT_TODO_ID` are migrated by `--audit` or before first
  `--add`, without renumbering existing TODOs.
- `uv run pytest tests/test_skills_install.py tests/skill-test-environment` passes.

## Distribution Plan

This ships through the existing Python package distribution. No new publishing
channel is needed.

Users get the installer behavior through the next `hermes-pipeline` release and run:

```bash
uv tool install --upgrade hermes-pipeline
tpo skills install --target all --reinstall
```

The bundled skill docs and test fixtures must be included in the wheel as package
data, preserving the existing `importlib.resources.files("hermes_pipeline.data")`
lookup.
