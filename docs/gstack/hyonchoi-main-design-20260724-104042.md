## Problem Statement

`hermes_pipeline/data/profiles/` currently mixes two unrelated domains under one
namespace: `pipeline/SOUL.md` is Hermes' identity/persona data, while
`gstack/phases.yaml` and `agent-skills/phases.yaml` are pipeline phase-orchestration
configs. Sharing a `profiles/` directory obscures the semantic distinction between
"who Hermes is" and "how pipelines run."

## What Makes This Cool

A small, satisfying refactor that makes the codebase's structure say exactly what
it means — separating identity data from orchestration config so the directory
tree stops lying about what's in it.

## Constraints

- Two code call sites load these paths via `importlib.resources`:
  `hermes_pipeline/phases.py:21` (`resolve_profile_phases_path`) and
  `hermes_pipeline/contract.py:170` (`bundled_profile_dir`).
- Packaging uses `packages = ["hermes_pipeline"]` in `pyproject.toml` (hatchling);
  no manifest/include-path changes needed for a directory rename.
- `pipeline/` subdirectory nesting under the identity path must be preserved
  (`data/hermes-identity/pipeline/SOUL.md`), to keep the identity data's internal
  structure intact — this was an explicit correction during the session, not a
  flattening.
- Doc scope is limited to public-facing guides that users read to understand the
  current layout: `docs/howto-pipeline-contract.md` and
  `docs/howto-agent-skills-profile.md`. Historical records (CHANGELOG.md, SPEC.md,
  `tasks/todo.md`, `tasks/plan.md`, `TODOS-archive.md`, and superpowers plan docs
  under `docs/superpowers/plans/`) describe past state and are intentionally left
  unmodified — they are a record of what was true when written, not a live
  reference.

## Premises

1. `data/profiles/pipeline/SOUL.md` (identity) and `data/profiles/{gstack,agent-skills}/phases.yaml`
   (phase configs) are genuinely different domains that happen to share a `profiles/`
   namespace. — AGREED
2. This is a pure path-rename refactor: two call sites, two docs, no behavior
   change, no packaging manifest change needed. — AGREED
3. New names: `data/hermes-identity/pipeline/SOUL.md` and
   `data/phase-profiles/{gstack,agent-skills}/phases.yaml`. — AGREED

Note: an initial premise proposed during the session — that `resolve_profile_phases_path`
had a bug where `pipeline/` would leak into the "available profiles" error listing — was
checked against the code and found false. `resolve_profile_phases_path` (phases.py:32-40)
already filters to dirs containing `phases.yaml`, so no bug exists. This was corrected
mid-session and the scope reduced to a pure split.

## Approaches Considered

### Approach A: Move + sed (minimal viable)
Summary: `git mv` the three dirs, update the two `.joinpath(...)` call sites, grep-fix docs.
Effort: S
Risk: Low
Pros: Smallest diff, git history preserved via `mv`, ships in minutes.
Cons: Docs updated by hand (easy to miss one); no test locks in the new layout.
Reuses: `resolve_profile_phases_path` / `bundled_profile_dir` unchanged in shape,
only path constants updated.

### Approach B: Move + sed + regression test (ideal)
Summary: Same as A, plus a small test asserting `bundled_profile_dir()` resolves under
`hermes-identity/` and `resolve_profile_phases_path("gstack")` resolves under
`phase-profiles/gstack/`, plus an assertion that the unknown-profile error message's
"Available profiles" listing still filters correctly post-move (does not list
`hermes-identity` or `pipeline` as a phase profile).
Effort: S/M
Risk: Low
Pros: Locks in the new layout so the namespaces can't accidentally re-mix later —
directly addresses the TODO's own stated risk ("easy to accidentally load wrong data type").
Cons: One more test file to maintain.
Reuses: same as A.

## Recommended Approach

**Approach B.** The TODO's rationale for existing is preventing accidental cross-domain
loading — a one-line regression test locking the resolved path shape is cheap insurance
directly against that risk, and adds only minutes to Approach A.
